# AGENTS.md

Flight software, ground station and telemetry tooling for BOLT (REXUS 37).
The human documentation in `docs/` is the reference. Read it rather than
guessing. This file covers only what cannot be inferred from the tree.

**Before contributing, read
[`docs/standards/ai/policy.md`](docs/standards/ai/policy.md).** Two rules
govern everything here: machine-checkable properties are checked by a
machine, and code the author cannot explain is removed rather than kept.

## Verify before claiming done

```bash
./scripts/verify.sh                        # everything
./scripts/verify.sh host-tests lint-flight # named stages; --list to see them
```

A change is not finished because it compiles.

## Two things that will bite you

**Most tracked files are generated.** CubeMX output under
`*/generated/`, csolution output under `*/RTE/`, and `lib/littlefs`.
Never edit or format those trees (`.claude/settings.json` enforces this
for Claude); reading them to understand vendor behaviour is fine. For
CubeMX output, change the `.ioc` and regenerate; only code inside the
user sections survives.

**The wire format is generated by C++26 reflection.** The
`WIRE(...)`/`PACKET(...)` annotations in `interfaces/include/bolt/wire/`
are the single source of truth. `interfaces/tools/generated/schema.json`,
`docs/interfaces/ICD-007-*.md`, `interfaces/tools/generated/icd-007.tex`
and `telemetry-tools/extension/src/protocol.gen.ts` are committed
*artefacts*. Never hand-edit them. To change a payload: edit the
annotated struct, run `interfaces/tools/schemagen/run-schemagen.sh`,
commit the regenerated files with the source change.
`docs/guides/changing-the-wire-format.md` walks the full sequence;
`docs/guides/` holds the other task procedures (firmware review, adding
a driver), tool-neutral for every assistant.

The drift check proves those artefacts agree with the annotation. It
cannot tell whether the annotation is right. A changed unit, scale,
offset or gate needs a person to check it against the datasheet.

## Build

CMSIS-Toolbox, not CMake. Contexts are `<project>.<Debug|Release>+<target>`:

```bash
cd flight-software
cbuild bolt.csolution.yml --context btc.Debug+btc
```

`flight-software/CMakeLists.txt` builds the host test suite only and never
produces a flight image. Host tests are Catch2. Firmware is `gnu++23` with
`-fno-exceptions -fno-rtti`; C++26 is used only by
`interfaces/tools/schemagen`.

## Invariants are binding

`docs/standards/system-invariants.md` defines P-1..4 and I-1..I-6. They
are requirements, and they are what code review cites. Most relevant when
writing firmware:

- **I-1**: the tick body fits the 40 ms budget (target 35 ms). The
  per-scope `*_TIMING` telemetry measures it in flight.
- **I-2**: every I2C, UART and CAN call has a bounded timeout. No
  unbounded waits on the critical path. SD writes are the documented
  exception and run off the critical path.
- **I-3**: no dynamic allocation after init. No `new`, `vector`,
  `string`, `function`. Fixed buffers and `std::array` only. The
  `invariants` verify stage rejects allocating `operator new` in any
  flight image; newlib's `malloc` presence is reported as an open item.
- **I-6**: never substitute a fallback for a bad reading. Set the
  `valid_mask` bit, or emit a `GAP_MARKER` with a reason.

**Layer boundary** (structural rule, not an invariant number): mission
logic under `btc/app/btc` and `btc/app/protocol` must not include
`main.h`, `stm32*` or vendor HAL headers; the HAL lives behind the
`board/` seam. The same check ratchets `shared/`: the allowlisted
platform files may touch HAL, a new one fails.

Check `HAL_*` return values. Do not discard them.

`Step` codes in `shared/utils/errors.hpp`, `StatusLeds::Fault` codes and
built-in test identifiers are wire-stable. Append inside the owning
module's range, never renumber, and update
`docs/handbook/fault-trace-codes.md` in the same commit.

## Writing

Prose in `docs/`, ADRs, ICDs, commit bodies and pull requests follows
`docs/standards/documentation/writing-style.md`. Content rules first:
every claim names its source, no sentence asserts that something is
important, and a paragraph that restates its heading is deleted. Say what
is not known rather than sounding complete about it.

Code comments follow `docs/standards/coding/cpp.md`: the *why*, never the
*what*, and none by default.

## Do not write these

Four categories are written by people, because they are the reference
everything else is checked against: the system invariants, the ADRs in
`docs/decisions/`, the expected value ranges for built-in test, and any
safety assessment. If a task requires one of them, say so and stop.

## Commits

Conventional Commits; see `docs/standards/process/commit-messages.md`.
A change produced with substantial assistance carries
`Assisted-by: <agent>:<model>` and a human `Signed-off-by:`. Never add a
`Signed-off-by:` line yourself: it certifies the right to submit and only
a person can certify that. See `docs/standards/ai/provenance.md`. The
hook (`git config core.hooksPath scripts/hooks`) and the `provenance`
verify stage enforce both rules.

Never commit to `main`. Work on a branch and open a pull request.

## Verification code gets reviewed harder

A defect in flight code is caught by the verification. A defect in the
verification makes everything downstream look correct. A new or changed
check therefore lands with a demonstration that it fails on a known-bad
input; the existing checks carry it as `--selftest`, which their verify
stage runs first. See `docs/standards/ai/tool-classification.md`.
